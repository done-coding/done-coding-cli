### 通用基础规则（1–5，不可修改）

1. [MUST] 每次新会话，在任何代码修改前先读本文件。
2. [MUST NOT] 将变更范围扩展到用户明确要求之外——不重构、不重命名、不重格式化非目标文件。
3. [MUST] 遵循仓库的 lint 和格式配置，声明任务完成前先运行 lint。
4. [MUST] 优先复用现有抽象，不创建冗余封装——修改前先搜索代码库。
5. [MUST] 行为变更时添加或更新测试，除非用户明确跳过。

### 通用工程原则（G1–G3，不可修改，全模板同文）

**G1. [MUST] 造新"轮子"前先联网核查现成方案**
判定（靠原则不靠清单）：要新建的一段能力，只要满足「① 解决通用问题（换个项目 / 别人多半也会遇到，非本项目独有业务规则）② 属于生态里常被现成封装的那类基础件」，即视为"轮子"，动手前 [MUST] 先联网检索是否已有更成熟、经大量生产验证的现成库 / 框架 / 标准做法，并在 spec 或提交说明留一句结论（选定方案，或坚持自研的理由 + 关键取舍）。
默认方向（堵后门）：拿不准算不算"轮子" → 一律按"是"处理，先查再说；[MUST NOT] 以"不在示例里 / 没想到有现成方案"为由跳过核查。
豁免（靠原则防过度触发）：纯本项目独有业务逻辑、一次性局部胶水 / 极小 helper、已被本仓现有抽象覆盖者（走规则 4）——免核查。
示例（仅说明"通用基础件"长什么样，非清单、非边界）：鉴权、缓存、队列、重试退避、限流、序列化、协议实现、ORM、连接池…… 凡此类"通用底座"皆属判定范围，不限于所列。

**G2. [MUST] 北极星：高内聚（一文件一职责）+ 低耦合（依赖单向、不造泥球）**
行数兜底信号（触发评估，非强拆）：≥ 600 行 🟡 停下自评内聚性；≥ 1000 行 🔴 兜底红线，判 god module → 拆或记债；副信号：单函数 ≥ 80 行 也黄灯（god module 病常在超大函数）。
豁免类（天然内聚、行数大不套线）：ORM 映射 / 枚举 / 配置 / 生成码 / 迁移脚本。
三条防误用护栏：ⓐ 行数是代理不是目标，[MUST NOT] 为凑数硬拆（碎片化比大内聚文件更糟）；ⓑ 拆分守 1:1 行为镜像，[MUST NOT] 把重构与 bug 修复搅一起；ⓒ 仅前瞻约束新增 / 在改文件，[MUST NOT] 据此对存量 god module 发起大重构（存量拆分单独排期）。
判据一句话：过线先问"该拆吗"——答"该"就拆、答"不该"留一句理由；[MUST NOT] 沉默放任，亦 [MUST NOT] 为数字硬拆。

**G3. [MUST] lockfile 是派生文件，不做手工 diff 审查 / 手工合并**
判定：`pnpm-lock.yaml` 等包管理器锁文件是依赖解析的派生物，`package.json`（或等价声明文件）才是真相源——[MUST NOT] 对 lockfile 做手工 diff 审查 / 手工合并（手工编辑易产出损坏锁文件）。
- rebase / merge 冲突：lockfile 冲突 [MUST] 撤销本地改动、保持传入版本（rebase 中 `git checkout --theirs <lockfile>`），随后重新 `pnpm install` 重新生成。
- 正常依赖升级（`pnpm add` / `pnpm install` 产生）的 lockfile 变更随功能提交，不适用本条。
